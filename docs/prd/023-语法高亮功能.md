## 1. 背景与目标

### 1.1 现状（已确认）

插件在 `package.json` 的 `contributes.languages`（package.json:112）注册了 12 个语言 ID
（sql / hive / mysql / spark / flinksql / postgresql / bigquery / sqlite / starrocks / sqlserver /
plsql / dameng）及其文件扩展名，但：

- **无 TextMate 语法**：`contributes.grammars` 不存在，无 `syntaxes/` 目录，仓库内无任何
  `.tmLanguage.json`
- **无语义高亮**：`src/` 下无 `registerDocumentSemanticTokensProvider` 相关代码

注册语言 ID 只决定"这是哪种语言"，不会带来着色。实际效果：

| 文件 | 当前表现 |
| ---- | -------- |
| `.sql` | 有高亮，但来自 VSCode 内置 SQL 语法，与本插件无关 |
| `.hql` `.mysql` `.sparksql` `.flinksql` `.psql` `.pgsql` `.bqsql` `.sqlite` `.sqlt` `.starrocks` `.sqlserver` `.pls` `.plsql` `.pck` `.pkb` `.dm` `.dameng` | **纯文本、无任何颜色**（除非用户另装三方插件） |

### 1.2 目标

1. 12 个已注册语言 ID 全部获得**方言感知**的语法高亮（各方言关键字/类型/内建函数/注释/字符串规则独立生成）
2. **零激活成本**：语法在 VSCode 渲染进程内 tokenize，不新增 activationEvents，不触碰扩展宿主
3. 数据**单一来源**：关键字/类型/函数全部复用现有 tokenizer 方言数据，不手工维护第二份清单
4. VSIX 体积增量 **< 0.5MB**（总量仍满足 ≤10MB 预算）

## 2. 方案选型

| 维度 | A. TextMate 声明式（推荐） | B. Semantic Tokens | C. 依赖用户自装三方插件 |
| ---- | ------------------------- | ------------------ | ---------------------- |
| 实现成本 | 低（声明式 JSON + 生成脚本） | 高（provider + 增量 tokenize + 生命周期） | 零 |
| 运行时成本 | 渲染进程，零扩展宿主开销 | 每次编辑触发扩展宿主词法/AST 计算 | 零 |
| 能力范围 | 词法级（关键字/字符串/注释/数字） | 语义级（表名/列名/CTE 着色） | 不可控 |
| 与 017 性能原则 | 完全兼容（不触碰任何 perf 基线） | 大 SQL（≥1MB）场景有性能风险 | — |
| 数据复用 | tokenizer 关键字系统直接复用 | 需接 SchemaCache / AST | — |
| 用户体验 | 开箱即用，无需激活插件 | 需插件激活后生效 | 不可控、不一致 |

**结论**：本期采用 **方案 A**；语义级高亮（表/列/CTE 着色）列为 v3.x 探查项（见 §13）。

## 3. 总体架构

```
src/dialects/<d>/<d>.keywords.ts      ─┐  keywords: string[] + dataTypes: string[]
src/dialects/<d>/<d>.functions.ts      ─┼─►  src/grammar/grammarBuilder.ts
src/grammar/dialectGrammarConfigs.ts   ─┘   （纯函数，输出语法对象）
src/grammar/keywordCategories.ts          （控制流/DDL/常量 分桶）
                                              │
                       scripts/generate-grammars.ts（tsx CLI，含校验）
                                              │
                       syntaxes/<id>.tmLanguage.json × 12（生成物入库）
                                              │
                       package.json contributes.grammars（12 条目）
                                              │
                       VSCode 渲染进程 tokenize（无需激活、无需 activationEvents）
```

设计要点：

1. **复用 generate-snippets.ts 脚本模式**（scripts/generate-snippets.ts）：tsx CLI + 生成物入库。
   与 snippetData 相同理由：构建环境不一定运行完整链路，生成物保留在 git 中。
2. **复用 tokenizer 关键字系统**（`src/dialects/<d>/<d>.keywords.ts`，扁平 `string[]`）。
   注意：与 hover 关键字系统（`src/dialects/keywords/*Keywords.ts`，`KeywordInfo[]` 富元数据）是
   **两套刻意分离的系统**（见 `src/dialects/keywords/index.ts` 顶部注释），本功能只取前者。
3. **builder 放 src/ 而非 scripts/**：`src/grammar/` 作为常规模块可被单测直接 import，
   scripts/ 仅作 CLI 入口（.vscodeignore 已排除 scripts/**，不进 VSIX）。
4. 与现有"参数高亮"（`src/providers/`，TextEditor 装饰）互不冲突：装饰是运行时叠加层，
   TextMate 是基础着色层，二者互补。

## 4. 方言语法规则矩阵（已固化，2026-10-19 核对）

核对结论（以代码为唯一事实来源，覆盖 §4 原表的全部"待核"项）：

1. **数据源升级**：各方言 formatter（`src/dialects/<d>/<d>.formatter.ts`）的 `tokenizerOptions`
   已内置完整的关键字分类（reservedClauses / reservedJoins / reservedSelect /
   reservedSetOperations / reservedKeywordPhrases / reservedDataTypePhrases /
   reservedFunctionNames / reservedDataTypes / reservedKeywords）与引号配置
   （stringTypes / identTypes / variableTypes / paramTypes / lineCommentTypes / operators）。
   生成器直接消费 `DialectOptions`，**取消**原计划的 `keywordCategories.ts` 手工分桶
   （§6.1 相应调整：三模块减为两模块）。
2. **规则顺序标准答案**：`src/lexer/Tokenizer.ts` 的规则数组（buildRulesBeforeParams →
   params → buildRulesAfterParams）本身是经过实战检验的优先级序列，TextMate 的
   first-match-wins 语义与之同构，生成器按此顺序一一转译。
3. **正则复用**：`src/lexer/regexFactory.ts` 的 `quotePatterns` / `stringPattern` /
   `prefixesPattern` / `identifierPattern` / `sortByLengthDesc` 输出纯字符串，
   与 oniguruma（TextMate 引擎）兼容（命名分组 `(?<tag>)`、`\k<tag>`、inline flags `(?i)`
   均支持）；JS 特有的 `[^]` 改写为 `[\s\S]`，`\p{Alphabetic}` 相关模式改用 ASCII 等价类。
4. **嵌套块注释**：`nestedBlockComments` 无任何方言启用（全仓 grep 为空），所有方言块注释
   均为标准 `/* … */` 非嵌套，用 begin/end 结构转译。

各方言关键差异（引自 `tokenizerOptions`，完整矩阵见各 formatter 文件）：

| 语言 ID | stringTypes 要点 | identTypes | 变量/参数 | 行注释 |
| ------- | ---------------- | ---------- | --------- | ------ |
| sql | N/U& 前缀 `''`，X`''` | `""` `` ` `` | `?` | `--` |
| hive | `''`/`""` 反斜杠转义 | `` ` `` | `${var}` | `--` |
| mysql | N/''，B/X raw | `` ` `` | `@var` `@@var` | `--` `#` |
| spark | raw R/X 前缀 | `` ` `` | `${var}` | `--` |
| flinksql | `''`/`""` 反斜杠转义 | `` ` `` | `${var}` | `--` |
| postgresql | E/U& 前缀，`$…$` | `""` `` ` `` | `:name`（named） | `--` |
| bigquery | r/b 前缀、`'''…'''` | `` ` `` | `@param` | `--` `#` |
| sqlite | `''` | `""` `` ` `` `[]` | — | `--` |
| starrocks | 同 MySQL base | `` ` `` | `@var` `?` | `--` `#` |
| sqlserver | N 前缀、X raw | `[]` `""` | `@var` `@@var` `?` | `--` |
| plsql | N 前缀、`q'…'` | `""` | `:bind` `&sub` | `--` |
| dameng | N 前缀 | `""` | `:bind` `&sub` | `--` |

**规则 include 顺序**（= Tokenizer 规则序的忠实转译，不得随意调整）：

```
block-comment → line-comment → quoted-identifier(identTypes) → number
→ keyword-phrases → data-type-phrases → case-control(CASE/WHEN/THEN/ELSE/END/BETWEEN)
→ logical-operators(AND/OR/XOR) → clauses → select → set-operations → joins
→ functions → data-types → keywords(分桶：TRUE/FALSE/NULL→constant.language)
→ parameters → variables → strings → operators → delimiters
```

**Scope 映射**（VSCode 内置 SQL 语法 + 主流惯例对照后的定稿，替代 §5 的预估表）：

| 元素 | Scope |
| ---- | ----- |
| 子句/集合/JOIN/其他保留字 | `keyword.other.sql` |
| CASE/WHEN/THEN/ELSE/END/BETWEEN | `keyword.control.sql` |
| AND/OR/XOR | `keyword.operator.logical.sql` |
| TRUE/FALSE/NULL | `constant.language.sql` |
| 数据类型（含短语） | `storage.type.sql` |
| 内建函数 | `support.function.sql` |
| 字符串 | `string.quoted.single/double/triple.*.sql`（按实际引号派生） |
| 引用标识符 | `` ` ``→`string.quoted.other.backtick.sql`；`[]`→`string.quoted.other.brackets.sql`；`"x"`→`string.quoted.double.sql`（主流 SQL 语法通行做法） |
| 数字 | `constant.numeric.sql`（负号归 operator，符合编辑器惯例） |
| 参数/变量 | `variable.parameter.sql` / `variable.other.sql` |
| 操作符 | `keyword.operator.sql` |
| 分隔符 | `punctuation.separator.comma.sql` / `punctuation.terminator.statement.sql` / `punctuation.section.parens.*.sql` |

## 5. Scope 命名规范

**已合并入 §4 的"Scope 映射"表**（对照 VSCode 内置 `sql.tmLanguage.json`——源自
microsoft/vscode-mssql——及 TextMate 通用惯例后定稿）。要点：

- 关键字一律 `keyword.other.sql`（内置语法同款），控制流 CASE 系列例外用 `keyword.control.sql`

- 字符串/引用标识符按 TextMate `string.quoted.*` 惯例派生（主流 SQL 语法通行做法）
- 常量 `constant.language.sql`、数字 `constant.numeric.sql`
- 所有 scope 以 `.sql` 结尾，兼容任意明暗主题

## 6. 生成器设计

### 6.1 文件清单

| 文件 | 职责 |
| ---- | ---- |
| `src/grammar/grammarBuilder.ts`（新增） | 纯函数 `buildGrammar(dialectOptions, meta): TmGrammar`；消费现成 `DialectOptions`，按 Tokenizer 规则序转译为 TextMate 规则 |
| `src/grammar/dialectGrammarConfigs.ts`（新增） | 12 方言元数据表（语言 ID ↔ `DialectOptions` 导入 ↔ 展示名 ↔ scopeName ↔ tmLanguage 文件名） |
| `scripts/generate-grammars.ts`（新增） | CLI：import 上述模块 → 写 `syntaxes/*.tmLanguage.json` |
| `syntaxes/*.tmLanguage.json` × 12（新增，生成物入库） | 最终语法文件 |

~~`src/grammar/keywordCategories.ts` 已取消~~（§4 核对结论 1：直接消费
`tokenizerOptions` 自带的关键字分类）。

### 6.2 生成器校验（写文件前强制，失败即退出非零）

1. 每个关键字/类型/函数名：转义正则特殊字符（`. * + ? ( ) [ ] { } | ^ $ \`）
2. 多词关键字：词间空白匹配 `\s+`（沿用 `reservedWord()` 的 `.replace(/ /gu, "\\s+")` 语义）
3. 关键字大小写不敏感：统一 `(?i)` 前缀 + `\b(?:…)\b` 词边界；同名条目去重后再拼接，
   且必须**按长度降序**（沿用 `sortByLengthDesc`，防止短前缀吞掉长短语）
4. 空列表、重复项、含前后空白的条目 → 报错
5. 输出 JSON 结构完整（name / scopeName / patterns / repository）

### 6.3 生成物示例（节选）

```jsonc
{
    "name": "HiveQL",
    "scopeName": "source.sql.hive",
    "patterns": [
        { "include": "#comments" },
        { "include": "#strings" },
        { "include": "#numbers" },
        { "include": "#variables" },
        { "include": "#operators" },
        { "include": "#keywords" },
        { "include": "#functions" },
        { "include": "#types" },
        { "include": "#identifiers" }
    ],
    "repository": {
        "keywords": {
            "patterns": [
                { "match": "(?i)\\b(?:SELECT|FROM|WHERE|…)\\b", "name": "keyword.control.sql" },
                { "match": "(?i)\\b(?:ADD|ADMIN|…)\\b", "name": "keyword.other.sql" }
            ]
        }
        // …
    }
}
```

### 6.4 npm 脚本集成

```jsonc
"generate-grammars": "npx tsx scripts/generate-grammars.ts",
"vscode:prepublish": "npm run generate-snippets && npm run generate-grammars && node esbuild.js --minify",
"esbuild-base": "npm run generate-snippets && npm run generate-grammars && node esbuild.js",
"esbuild": "npm run generate-snippets && npm run generate-grammars && node esbuild.js"
```

### 7.1 关键决策：覆盖内置 `sql` 语法

为 `sql` 语言 ID 注册 grammar 会覆盖 VSCode 内置 SQL 语法（扩展优先于内置）。**推荐覆盖**：

- 各方言文件与 `.sql` 文件获得一致的着色质量与规则集（嵌套注释等能力内置语法不具备）
- 关键字来源为 `sql/sql.keywords.ts`，与插件方言体系一致
- 采用标准 scope（§5），主题着色不受影响
- **回滚成本极低**：删除 `grammars` 中 `sql` 一条即恢复内置行为

风险与验收要求见 §11 / §10（`.sql` 前后对比为必做验收项）。

### 7.2 无需改动的部分

- **activationEvents**：grammar 为纯声明式贡献，VSCode 渲染进程直接加载，无需激活插件
- **package.nls*.json**：grammar 不含用户可见文案，无 i18n 条目
- **`hive-sql` / `flink-sql` / `postgres` / `oracle` 等别名 ID**：非本插件注册的语言，语法覆盖
  出于兼容性考虑暂不处理（方言功能层面 dialectRegistry 已支持）

## 8. 测试策略

### 8.1 单元测试（`src/test/grammar.test.ts`，并入现有 mocha 套件）

1. **结构校验**：12 份 JSON 均含 name/scopeName/patterns/repository；scopeName 唯一
2. **一致性校验**（沿用 `configConsistency.test.ts` / `dialectConsistency.test.ts` 模式）：
   - `contributes.grammars` 的 language 集合 ⊆ `contributes.languages` 的 ID 集合
   - 每条 path 指向的文件存在，且文件 scopeName 与声明一致
3. **行为校验**：从生成物提取 keyword 正则，断言 `select`（小写）命中、`selection` 不命中
   （词边界）、含特殊字符的关键字已转义
4. **再生成一致性（golden）**：import `buildGrammar` 重新生成并与磁盘文件比对，
   防止关键字更新后语法文件漂移

### 8.2 tokenize 冒烟测试（新增 devDependencies：`vscode-textmate` + `vscode-oniguruma`）

规则顺序错误（注释 vs 操作符 vs 字符串竞争）是 TextMate 语法最典型的故障模式，仅靠正则单测
无法覆盖，因此引入 VSCode 自身使用的 tokenize 引擎做真实冒烟（vscode-oniguruma 为 WASM 实现，
纯 JS、无原生模块，仅 devDependencies，不进 VSIX）：

```ts
// src/test/grammar.test.ts（节选）
const registry = new Registry({
    onigLib: onigLibPromise, // 加载 oniguruma WASM
    loadGrammar: async (scopeName) => parseRawGrammar(
        fs.readFileSync(scopeToFile[scopeName], "utf8"), ".json"),
});

it("hive: 注释优先于操作符，关键字词边界正确", async () => {
    const g = await registry.loadGrammar("source.sql.hive");
    const line = g.tokenizeLine("select x, selection from t -- not-an-operator", INITIAL);
    // 断言：select → keyword.other.sql；selection → 不命中关键字；
    //       '-- not-an-operator' → comment.line.*（而非 keyword.operator）
});
```

**实施调整**：未采用独立的 `src/test/fixtures/grammar-samples/*.sql` 样例文件，改为
**行内样例**（每个 test 直接 tokenize 一行/多行输入并断言 scope）——断言与输入同处一处，
可读性更高，且省去 12 个 fixture 文件的管理成本。覆盖场景不变：每方言至少覆盖
行/块注释、跨行结构（块注释/美元引号/三引号）、方言引号、变量/占位符、函数括号前瞻。

**实施结果（2026-10-19）**：19 个用例全部通过（结构/一致性 4 + tokenize 15）。
`npx mocha --ui tdd out/test/grammar.test.js` 可脱离 VSCode 直接运行（diSetup 拉入 vscode
模块，本测试不需要 DI，直接省略 --require）。经 `.vscode-test.js` 全量运行时同样正常：
`@vscode/test-cli` 的 runner 默认 `ui: 'tdd'`，与项目现有测试风格（lexer.test.ts 等
suite/test）一致，无需额外配置。

## 11. 风险与缓解

| 风险 | 影响 | 缓解 |
| ---- | ---- | ---- |
| 规则顺序错误（注释/操作符/字符串/变量竞争） | 高亮错乱 | §4 固定 include 顺序 + §8.2 tokenize 冒烟断言顺序 |
| 覆盖内置 `sql` 后 `.sql` 体验回退 | 存量用户可感 | 规则集对标内置 + martinring 取超集；§8.3 前后对比为必做验收；单条目可即时回滚 |
| 关键字含正则特殊字符或多词条目 | 生成物错误 | 生成器强校验 + 转义；多词以 `\s+` 连接；异常形状构建即失败 |
| 语法文件漂移（方言关键字更新后未再生成） | 高亮滞后 | golden 再生成测试 + prepublish 链强制再生成 |
| 主题 scope 不兼容导致颜色缺失 | 视觉缺陷 | 统一标准 scope 前缀（§5）+ 明暗主题人工核对 |
| VSIX 超体积预算 | 发布受阻 | 预估增量 200-300KB；打包后核对；必要时裁剪 functions 列表 |
| `$` 系规则冲突（PG `$tag$` vs `$1` vs 操作符） | PG 方言错乱 | strings 先于 variables 先于 operators 的固定顺序 + PG 专项样例 |
| PG/StarRocks 关键字表缺 `AS`（格式化器经 identAlias 后处理，tokenizer 不识别） | 别名不着色 | 已缓解：builder 统一注入 `keyword.other.alias.sql` 规则（§4 实施注记） |
| oniguruma 与 JS RegExp 方言差异（`(?i)` 前缀、`[^]`、`\p{}`） | 生成物在编辑器中失效 | 生成器校验禁用 JS 特有模式；校验正则时剥离 oniguruma inline flag（§6.2） |
